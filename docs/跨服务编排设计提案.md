# 跨服务编排设计提案

> 单项目的 sub-agent/AGENTS.md 已经成型(七阶段流程)。但当一个需求要**改多个微服务**(比如会员服务改接口、私域服务改调用、销管服务改字段),单项目编排就不够了——跨服务的契约变更、依赖顺序、并行协调是更难的题。
>
> 本文档是**设计提案**,综合业界范式(Spine Pattern、Lead-Teammate 编排、契约先行),融合进我们的 sub-agent 体系。**诚实标注:未经真实多服务项目验证,是方向性设计,不是已落地做法。**

---

## 0. 为什么跨服务更难

单项目编排,AI 在一个 context 里看全所有代码。跨服务时:

| 难点 | 单项目 | 跨服务 |
|---|---|---|
| **上下文** | 一个仓库,读得到 | 散在多个仓库,AI 冷启动不知道有哪些服务 |
| **契约变更** | 改自己就行 | 改 A 服务接口,B/C 服务的调用全要同步,漏一个就生产崩 |
| **依赖顺序** | 文件级依赖 | 服务级依赖(A 先发,B 才能改调用) |
| **并行协调** | 一个 agent 串行 | 多个 agent 并行改不同服务,谁先完成、怎么对齐 |
| **回滚** | git revert 一个仓库 | 多仓库要一起回滚,顺序错了更糟 |

> 核心矛盾:**AI agent 的 context 是单仓库的,但业务变更是跨仓库的**。

---

## 1. 业界两种主流范式(调研结论)

### 范式 A:Spine Pattern(元仓库 + 分层路由)

来自 [tsoporan.com 的 Spine Pattern](https://tsoporan.com/blog/spine-pattern-multi-repo-ai-development/)。核心思路:**建一个单独的"元仓库"(spine),只放编排信息,不放代码**。

```
spine/                          ← 元仓库(单独 git)
├── CLAUDE.md                   ← 全局导航:系统全景、服务清单、架构决策
├── _tasks/                     ← 跨服务任务文件
│   └── 2026-07-会员字段改造.md  ← 一个跨服务需求一个任务文件
└── refs/                       ← 各服务的引用(不引代码,引文档)
    ├── 会员服务.md              ← 会员服务的能力边界、接口清单
    ├── 私域服务.md
    └── 销管服务.md
```

**关键洞察**:"spine 追踪的是编排,不是代码。它是 context 在会话间存活的地方。"

**工作流**(三步):
1. **计划**:在 spine 仓库里和 AI 多轮探索,产出跨服务任务文件
2. **提交结构**:任务文件固化"改哪些服务、依赖顺序、契约定义"
3. **并行执行**:开多个 session,每个改一个服务,任务文件做共同上下文

**适用**:多仓库、前后端分离、不同语言框架的复杂迁移。
**不适用**:Monorepo(没必要);单人小项目(过重)。

### 范式 B:Lead-Teammate 编排(主代理 + 队友代理)

来自 [krishnal.com 管 9 个微服务的实战](https://krishnal.com/blog/developer-as-orchestrator-ai-coding-agents)。核心思路:**一个主代理规划派发,多个队友代理并行执行,契约变更在代理间直接沟通**。

**工作流**:
1. **主代理(Lead)**收到需求 spec,识别受影响的服务,定依赖顺序
2. **派 Teammate**——每个受影响的服务一个 teammate agent
3. 每个 teammate **先写 PLAN.md**(不急着写码),主代理汇总成 master plan
4. **并行实现**:teammate 各改各的服务,准备各自的 PR
5. **契约直接沟通**:B 服务的 teammate 需要 A 服务的新接口形状,**直接问 A 的 teammate**,不用人类居中传话

**关键原则**:"编排者的首要职责是定义 agent 任务之间的干净接口。"
**踩坑**:① 初期反而变慢(J 曲线)② 别所有任务都用最强模型(成本爆)③ 拆解不当=级联失败 ④ 不是每个任务都需要编排器。

## 2. 我们的设计:融合方案

把 Spine Pattern(元仓库)和 Lead-Teammate(主队友编排)融合,套进我们已有的 sub-agent 七阶段体系。

### 核心架构:spine 元仓库 + 跨服务七阶段

```
spine/                          ← 跨服务元仓库(新建,每个业务域一个)
├── AGENTS.md                   ← 跨服务编排指令(本提案的落地版)
├── system-map.md               ← 服务全景:有哪些服务、各自能力边界、依赖关系
├── contracts/                  ← 契约注册表(接口/消息体/数据模型的权威定义)
│   ├── api-member.yaml         ← 会员服务对外接口契约
│   ├── api-private.yaml        ← 私域服务
│   └── events.yaml             ← MQ 事件契约
├── _tasks/                     ← 跨服务任务文件(每个需求一个)
│   └── 2026-07-会员字段改造.md
└── refs/                       ← 各服务引用(指向真实仓库 + 关键文档)
```

> spine **不放代码**,只放"对系统如何协同的理解"。各服务代码仍在自己的仓库。

### 跨服务七阶段(单项目七阶段的扩展)

| 阶段 | 单项目版 | **跨服务版(扩展)** |
|---|---|---|
| ① 澄清 | grill-me 盘问需求 | 同 + 额外问清"涉及哪些服务、是改造还是新建" |
| ② 选包 | /vibe 选方法论包 | 同 |
| ③ 契约 | openspec 写单项目 spec | **关键扩展**:先写 **spine/contracts/** 的跨服务契约(接口形状、事件格式),这是所有服务的共同基线 |
| ④ 拆派 | 拆任务 + 定 subagent | **扩展**:按服务拆——每个受影响的服务一个 teammate agent;定依赖顺序(A 先 B 后) |
| ⑤ 实现 | 主 agent + subagent 编码 | **Lead-Teammate**:主代理协调,teammate 各改各的服务,契约变更 teammate 间直接沟通 |
| ⑥ 审查 | code-review + ponytail | 同 + **额外审契约一致性**(各服务改动是否符合 contracts/) |
| ⑦ 验证归档 | 跑测试 + 回写 spec | 同 + **跨服务集成验证**(契约兼容、依赖顺序正确)+ 回写 spine/contracts/ |

### 关键设计点

**① 契约先行(Contract-First)**
跨服务的最大风险是契约变更。**③ 契约阶段必须先把 contracts/ 定下来**,各服务的实现都以它为准。
> 对应业界共识:"跨服务需求的核心风险往往在契约变更,把契约先固化到文档里,比让 AI 一口气改完所有服务要可控得多。"

**② Teammate 间直接沟通,不用人类传话**
B 服务 teammate 需要 A 服务的接口形状 → 直接读 contracts/(或直接问 A 的 teammate)。**编排者(你)只管定义干净接口,不居中传话。**

**③ 按依赖顺序派发**
主代理定顺序:provider 先(改接口的),consumer 后(改调用的)。teammate 按序启动,不能乱并行。

**④ 每个 teammate 自带单项目七阶段**
每个 teammate 改自己那个服务时,跑的是单项目的 AGENTS.md 七阶段(澄清→实现→验证)。spine 的跨服务编排是**上层协调**,不替代单项目流程。

## 3. 决策点(什么时候用跨服务编排)

**不是所有多服务需求都要这套**。参考管 9 微服务那篇的教训——"不是每个任务都需要编排器"。

| 涉及服务数 | 建议方案 | 理由 |
|---|---|---|
| **1 个** | 单项目 AGENTS.md | 就是单项目,不用跨服务 |
| **2-3 个** | 轻量跨服务:在对话里定契约 + 手动开多 session | 不值得建 spine 元仓库,口头/文档协调即可 |
| **3-5 个** | **建 spine 元仓库 + Lead-Teammate**(本提案) | 契约复杂度上来,值得正式编排 |
| **5+ 个** | spine + Lead-Teammate + 重点审契约 | 瓶颈通常在人工 review,不在 AI |

> **红线**:涉及契约变更(接口/消息体/数据模型)的跨服务需求,**必须**走契约先行,不管几个服务。

## 4. spine/AGENTS.md 骨架(跨服务编排指令)

这是放进 spine 元仓库的编排指令(区别于单项目的 sub-agent/AGENTS.md):

```markdown
# 跨服务编排 AGENTS.md

## 你是 Lead Agent(主代理)
- 收到跨服务需求 → 识别受影响服务 → 定依赖顺序 → 派 Teammate
- 你的职责:定义干净接口、协调顺序、汇总产出。不亲自写业务代码。

## ③ 契约先行
- 改 contracts/ 先于任何实现
- 契约定不下来,禁止进入 ⑤ 实现

## ④ 按服务拆 Teammate
- 每个受影响服务一个 teammate
- 给 teammate:任务边界 + contracts/ 相关段 + 验收标准
- 不给:其他服务的完整代码(只给契约)

## ⑤ Teammate 协作
- teammate 间契约问题:直接读 contracts/ 或问对应 teammate
- teammate 各自跑单项目七阶段(改自己的服务)
- 完成后准备各自 PR + 契约一致性自检

## ⑥ 跨服务审查
- 审各服务改动是否符合 contracts/
- 审依赖顺序(provider 先 consumer 后)

## ⑦ 跨服务集成验证
- 契约兼容性测试
- 依赖顺序正确
- 回写 contracts/ 和 system-map.md
```

## 5. 和单项目 sub-agent 的关系

```
跨服务 spine/AGENTS.md(上层·协调多服务)
        ↓ 每个服务派一个 teammate
单项目 sub-agent/AGENTS.md(下层·改单个服务)
        ↓ teammate 跑单项目七阶段
   ① 澄清 → ② 选包 → ... → ⑦ 验证
```

> **跨服务编排不替代单项目编排,是在它上面加一层协调。** 每个 teammate 干活时,用的还是单项目 AGENTS.md 那套七阶段。

## 6. 已知风险(诚实标注)

| 风险 | 说明 | 缓解 |
|---|---|---|
| **未经真实验证** | 本提案是设计,没在真实多服务项目跑过 | 先在 2-3 服务的轻量场景试,跑顺了再扩 |
| **J 曲线** | 初期可能比手动改还慢(要建 spine、定契约) | 接受前几次慢,沉淀出 system-map/contracts 后加速 |
| **teammate 间沟通成本** | 多 agent 协调本身有开销 | 小需求别用,3+ 服务且涉及契约才用 |
| **契约维护负担** | contracts/ 要跟着代码变,容易脱节 | ⑦ 归档阶段强制回写;Hook 可检查"改了接口但没改 contracts/" |
| **context 爆** | 跨服务信息量大 | teammate 只给契约段不给全代码(对应 context-engineering 技能①) |

---

## 7. 落地路径(建议)

1. **先不建 spine**——挑一个近期的 2-3 服务需求,用"轻量跨服务"(对话里定契约 + 手动多 session)试一次,看痛点
2. **痛点确认后建 spine**——把试出来的契约格式、服务清单固化进 spine 元仓库
3. **跑 Lead-Teammate**——第三个跨服务需求开始,正式用主队友编排
4. **迭代**——按真实反馈调依赖顺序判断、契约格式、teammate 派发粒度

> **别一上来就建完整 spine**——先用轻量方式验证"契约先行 + 分服务派发"这个核心思路在你这儿成不成立。
